1. 這套系統是什麼

一個以 Reflex（Python 全端框架）建置的桌面版 Web Dashboard， 把 Lotus Notes 的郵件與 LLM 的分析結果，整理成「今天要處理什麼」的決策畫面。

1

與擷取分析系統的分工

郵件的擷取與 LLM 分析由另一套 pipeline（personal_assistant_v2）完成。 本系統只負責「呈現」，兩者的交界面就是 pipeline 輸出的 daily_reports/ 資料夾——Dashboard 只讀它，不寫它。

2. 做什麼、不做什麼

做不做
整理今日重要郵件、待辦、Deadline、設備事件 取代 Lotus Notes
顯示 AI 摘要、行動項目、建議處置、回覆草稿 自行呼叫 LLM（分析在 pipeline 端完成）
依原始順序呈現郵件的文字、圖片與表格 連線 Lotus Notes 或使用 COM
以自然語言查詢當日郵件（Ask AI） 實際寄信或自動回覆
把重複的系統告警聚合成事件 寫入任何公司系統（唯讀）
可離線展示 Mock 模式內建 24 封範例郵件與 5 張示意圖，不需要公司環境、Lotus Notes 或任何 API， reflex run 就能完整操作所有頁面。

3. 核心設計原則

UI 與資料來源完全解耦。這是整個專案所有結構決策的來源。

系統從一開始就預期要在兩種環境執行：個人電腦（假資料）與公司電腦（真實資料）。 因此格式差異一律由最底下兩層吸收，上層完全不知道資料從哪裡來。

切換資料來源

# 假資料，可完全離線展示
$env:MAIL_DASHBOARD_DATA_MODE = "mock"

# 公司 pipeline 的真實輸出
$env:MAIL_DASHBOARD_DATA_MODE = "real"
驗收標準 切換模式時，pages/、components/、states/、 services/、models/ 都不需要修改。 若發現非改不可，代表有東西寫死在不該寫死的地方。

4. 分層與職責

層可以做不可以做
components/ 顯示傳進來的 Model 讀檔、知道檔案路徑、知道 Notes 或 LLM 存在
pages/ 組合 component、定義版面 同上
states/ 存畫面狀態、呼叫 Service 業務判斷、import repositories
services/ 分類、篩選、搜尋、統計 知道資料是 JSON 還是資料庫
repositories/ 決定資料從哪讀、如何載入 決定資料怎麼顯示
adapters/ 吸收外部格式差異 業務判斷
常見誤用 UI 不應該自己寫 mail.ai.importance >= 4，而是呼叫 mail_service.get_important_mails()。 「幾星算重要」的定義改變時，只需要修改 services/mail_service.py 一個檔案。

顯示用的值一律預先算好

Model 內所有 UI 要顯示的字串（時間標籤、星號、期限文字、檔案大小…） 都是實體欄位，由 Adapter 在建立物件時一次算完。 不使用 @property，因為 Reflex 的 Var 無法存取 property， 而且元件本來就不該做資料加工。

5. 資料流

Mock 模式

app/mock_data/*.json
    → MockMailAdapter        欄位改名、單位換算、衍生值計算
    → MockMailRepository     載入時把日期整體平移到執行當天
    → Service → State → UI

Mock JSON 的日期錨定在 MOCK_ANCHOR_DATE， 載入時會平移到執行當天，因此任何一天打開 Demo，「今日總覽」都有資料。 這是 Repository 的內部行為，上層完全不知情，換成 real 模式時不會有殘留邏輯。

Real 模式

daily_reports/
  <YYYY-MM-DD>[-批次後綴]/
      mails/mail_NNNN/mail.json          ← Step A 產出
      mails/mail_NNNN/body_image_*.gif   ← 郵件內嵌圖片
      summaries/mail_NNNN_summary.json   ← Step C 產出
      daily_digest.md                    ← Step D 產出
          ↓
  CompanyMailAdapter    吸收格式差異
          ↓
  RealMailRepository    依日期分組、聚合告警、合成今日重點
          ↓
  Service → State → UI
同一天的多個批次會自動合併 2026-08-07 與 2026-08-07-MAIL41_TO_MAIL64 會依資料夾名稱開頭的日期歸為同一天。

檢視日期切換

Header 的日期為下拉選單，可選的日期就是輸出目錄下有資料的那幾天。 預設看今天；今天沒有資料時退回最近一天，並在旁邊標示原因， 避免看到空白首頁卻不知道為什麼。

切換日期時，Repository 的 reference_date 跟著改變， 所有「今日 / 昨日 / 本週」的統計都會即時重算—— Service 的「今天」是動態讀取而非建構時算死的。

郵件圖片

模式圖片位置提供方式
mockassets/mock/images/Reflex 靜態檔案
realdaily_reports/ 內後端掛載的 /mail-assets 唯讀路由

真實郵件的圖片不能整包複製到 assets/， 因此在 app/main.py 掛一個靜態路由指向輸出目錄。 元件只拿到一個可用的 URL，不需要知道兩者的差別。

7. Schema 對應

公司 pipeline 的輸出格式若改變，只修改 adapters/company_adapter.py， 不要動其他任何一層。

mail.json → Mail

內部 Model公司欄位處理方式
mail_idmail_id直接對應
subjectsubject移除結尾的資料分級標記
senderfrom（純字串，4 種格式）_parse_sender() 解析
sent_atdate（只有日期）補 00:00；time_label 留空
content_blocksblocks（image 用 path）欄位改名 + 組圖片 URL
to / ccto / cc直接對應（值可能是群組名）
is_read / attachments無一律當未讀 / 空清單

from 欄位的四種格式

寄件者是純字串而非結構化物件，且格式不統一，解析器四種都要處理（以下為示意值）：

"Alert System" <alert-system@example.com>
Alert System <alert-system@example.com>
CN=Some User/OU=DEPT/O=ORG           ← 沒有 email
Some User/DEPT/ORG                   ← 沒有 email

summary.json → AIAnalysis

內部 Model公司欄位處理方式
categorycategory（7 種值域）對照表轉換
importance（1–5）priority（high/medium/low）三級轉五級，見下
todosaction_items改名
key_pointskey_points純字串陣列，條列顯示
key_facts無公司端沒有 label/value 配對
action_requiredreply_needed + category綜合判定
addressed_toaddressed_to_medirect / cc / broadcast
deadlinedeadlineStep C 保證為 YYYY-MM-DD 或空字串
recommendationsrecommendations直接對應
reply_draftreply_draft直接對應

三級 priority 轉五級 importance

基礎分   high = 5 / medium = 3 / low = 1
  +1     category 是 urgent 或 action_required
  +1     addressed_to_me == "direct"
上限 5

單看 priority 會壓縮太多資訊：實際資料多半只有 low 與 medium， 全部落在 1 或 3 星，「重要郵件」永遠是 0 封。 因此納入另外兩個公司端已經判定好的訊號。 這是刻度換算（屬於格式差異）所以放在 Adapter； 「幾星算重要」的門檻仍由 MailService 決定。

舊批次相容 deadline、recommendations、reply_draft 是後期才加入 Step C 的欄位。舊批次的 summary 沒有這三項時一律容錯為空值， UI 會自動隱藏對應區塊，不需要回頭重跑舊資料。

8. 告警處理

公司資料沒有獨立的告警檔，系統事件是從 category == "machine_alert" 的郵件推導出來的。

本文是空的，資訊在主旨

這類告警信的 blocks 多半是空的（擷取階段抓不到本文）， 但主旨是固定格式，所有資訊本來就在主旨裡， 因此不需要回頭修改擷取邏輯，由 alert_parser.py 解析即可。 

【汙染因子超標通知】X1 關鍵機台 X1_TOOL_03 - PSN X1_TOOL_03#P1 狀態 OOS
                  ^^  ^^^^^^^^  ^^^^^^^^^^        ^^^^^^^^^^^^^  ^^^
                  區域   關鍵性      機台              PSN 點位     狀態

（機台代號為示意值）

聚合

同類告警依 alert_key 聚合，避免事件頁被同一種告警灌滿； 卡片上以 ×N 標示出現次數。 關鍵機台的超標告警自動升為嚴重。

告警類型嚴重度來源欄位
汙染因子超標（關鍵機台）嚴重主旨解析
汙染因子超標（非關鍵）警告主旨解析
裝置斷線 / 離線警告主旨解析
自動派報 / 其他資訊alert_type
上游規則有誤判 pipeline 以寄件者與主旨關鍵字快速分流告警， 部分公告類郵件（如 HR 通知）會誤判為 machine_alert。 這類郵件無法解析出機台，事件卡片會顯示「—」。 要根治需調整 pipeline 端的分流規則，非 Dashboard 可解。

11. 移機到公司電腦

五個步驟，不需要修改任何 .py 檔。

  1. 重建虛擬環境——.venv/ 不要複製，裡面有絕對路徑。 python -m venv .venv 後重新 pip install -r requirements.txt。
  2. 指定資料模式：$env:MAIL_DASHBOARD_DATA_MODE = "real"
  3. 確認找得到 pipeline 輸出—— 系統會自動從專案根目錄往下搜尋名為 daily_reports 的資料夾。 若在專案外（網路磁碟、其他磁碟機），設定 MAIL_DASHBOARD_REAL_DATA_DIR。
  4. 確認找得到身分設定檔——同樣自動搜尋 alert_config.json。找不到會退回預設的展示身分。
  5. 檢查 port 未被佔用。

驗證是否接上

啟動後開 /settings，該頁刻意把所有路徑攤開顯示，逐項確認：

項目應該顯示
DATA_MODEreal，不是 mock
狀態OK — <日期> 共 N 封郵件，不是「找不到目錄」
公司資料目錄指向正確的 daily_reports
使用者身分你的名字，不是預設的展示身分
不要複製 pipeline 的輸出目錄 真實郵件資料與 pipeline 設定檔含機敏內容，且公司電腦上 pipeline 本來就會產出。 這兩者已在 .gitignore 中排除，不會進入版控。

14. 開發注意事項

兩個 Reflex 特有的陷阱，錯誤訊息完全看不出真因。

① dataclass 欄位不可與 Var 方法同名

items、to、keys、values 都是 Reflex ObjectVar 上的真實方法。 欄位取這些名字時，block.items 會取到方法本身而不是欄位。 

TypeError: Cannot pass a Var to a built-in function.

因此 ContentBlock 的清單欄位命名為 list_items 而非 items。

② rx.icon(tag) 的 tag 必須是編譯期常數

Reflex 要據此決定 import 哪個圖示，傳入 Var（含 rx.match / rx.cond 的結果）會噴出同一句錯誤。 正確做法是先把每種圖示各建成一個元件，再用 rx.match 挑元件： 

rx.match(
    item.icon_key,
    *[(key, rx.icon(tag, size=16)) for key, tag in ICONS.items()],
    rx.icon("file", size=16),
)
補充 Var 可以用在 f-string（f"{State.count} 封" 正常運作）， 所以看到這句錯誤時不必往 f-string 方向查。
