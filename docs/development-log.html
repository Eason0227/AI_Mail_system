2. token 都花在哪裡

最反直覺的一點：輸出只佔總量的 0.47%。 真正的消耗來自每次 API 呼叫都要重送整份對話。

S1    31 次呼叫 ÷ 2,199,135 輸入 token  =  平均 70,940 / 次
S2   308 次呼叫 ÷ 81,651,659 輸入 token =  平均 265,102 / 次   ← 3.7 倍

S2 的總量是 S1 的 36 倍，但輸出只有 3.7 倍。 差距全部來自「對話變長」× 「呼叫變多」的乘積效應。

對成本的實務啟示 減少 token 最有效的方式不是「少寫程式」，而是把長任務切成獨立的 session。 同一個 session 內每多問一輪，前面所有內容都會再被計費一次。

S1 的 25 分鐘產出 1,300 行、只用 83 K 輸出 token——因為那是「照規格寫新檔案」， 沒有未知數。S2 則有大量 token 花在不產生程式碼的活動：

  • 讀取既有的擷取分析 pipeline 原始碼
  • 統計 64 封真實郵件與 64 份分析結果，歸納實際 Schema
  • 每次改動後重跑兩種資料模式 × 15 條路由的編譯檢查
  • 逐條驗證告警主旨解析（48/52 命中，4 筆確認為上游誤判）
  • 推送前掃描機敏資料

這些不產生程式碼，但它們是「敢說兩模式都通過」的依據。

5. 有效的做法

先定介面，再填實作

S1 結束在「抽象介面剛定義完，還沒有任何實作」。這個中斷點看似尷尬， 實際上讓 S2 接手時沒有任何架構爭議——合約已經寫死，只要填空。

把驗證做成一行指令

不需要啟動伺服器就能逐頁編譯，是整個專案最有價值的一條指令。 它把「改了會不會壞」從幾分鐘縮短到幾秒： 

python -c "import app.main as m; [m.app._compile_page(r, save_page=False) for r in m.app._unevaluated_pages]"

同理，一支獨立的 State 流程腳本可以在不開瀏覽器的情況下， 跑完「載入 → 搜尋 → 篩選 → 選信 → 產生草稿 → 勾待辦 → 問答 → 跨頁跳轉」全鏈路。

每個決定都留下理由

程式碼註解不只寫「做了什麼」，而是寫「為什麼這樣做、以及不能怎麼改」。 例如欄位為何叫 list_items 而不是 items、 為何顯示用的值要預先算好而不用 @property。 這讓跨 session 接手時不需要重新推導。

用真實資料反推規格

真實資料接上之前，先統計 64 封郵件的欄位覆蓋率、分類分佈與格式變異， 再決定 Adapter 怎麼寫。這一步找出了幾個從規格看不出來的問題： 寄件者有四種格式、告警信本文是空的、三級 priority 直接映射會讓「重要郵件」永遠是 0。

6. 踩到的坑

問題徵狀教訓
欄位名撞框架保留字 錯誤訊息完全不提名稱衝突 框架的 Var 物件有自己的方法，資料欄位不可同名
圖示標籤傳入動態值 與上者相同的錯誤訊息 編譯期才能決定的參數不能傳執行期的值
路徑寫死 換一台電腦就失效 改為環境變數優先、否則自動搜尋
統計基準在建構時算死 切換檢視日期後數字不更新 會變動的基準要做成動態讀取
空欄位當成產生失敗 按鈕按下後出現無說明的空白框 「沒有資料」與「還沒產生」是兩種狀態
最有價值的一次修正 真實資料接上後才發現：上游不提供回覆草稿欄位，但介面仍顯示可編輯的空白框。 這種問題只有實際跑真資料才會浮現，Mock 資料永遠測不出來。

7. 效率換算

指標數值
每行程式碼的輸出 token約 45
每則使用者訊息產出的程式碼約 383 行
每則使用者訊息的工具呼叫約 16 次
輸出 token 佔總量0.47%

「每則訊息 383 行」這個數字要小心解讀——它包含大量既有檔案的重寫， 且不代表可以無限拉高。訊息數少的真正原因是每則訊息帶的資訊量高： 完整的需求規格、明確的檔案路徑、以及對前次結果的具體回饋。

數據自 Claude Code 的 session 逐字記錄統計。 同一則助理訊息可能分多行寫入，統計 token 時依訊息 ID 去重， 統計工具呼叫時則逐一計算——兩者的處理方式不同，混用會得到錯誤結果。
